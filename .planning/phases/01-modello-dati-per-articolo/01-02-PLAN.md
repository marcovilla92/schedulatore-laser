  <name>Task 1: Rewrite create_order and phase operations for per-article tracking</name>
  <files>app/backend/database.py</files>
  <action>
Rewrite the OrderManager class in database.py. Add `Article` to the imports from `.models`.

**`create_order()` changes:**
- After creating the Order record, create `Article` records in the `articles` DB table for each article dict passed in
- For each Article record, create ProcessingStep records — one per phase in that article's `required_phases`
- Each ProcessingStep now gets `article_id` set to the Article's UUID (in addition to `order_id`)
- Still populate `order.articles` JSON column for backward compat (keep existing behavior)
- Still populate `order.required_phases` as union of all article phases (keep existing behavior)
- Default `required_phases` for articles: all 5 phases ['LASER', 'PIEGA', 'SALDATURA', 'PULIZIA', 'SPEDIZIONE'] per user decision
- If no articles provided, create a single "default" Article with all phases (handles edge case of orders created without articles)

**`start_phase()` changes:**
- Accept optional `article_id` parameter (in addition to existing `order_id` + `phase`)
- If `article_id` provided: start the specific ProcessingStep for that article+phase
- If `article_id` NOT provided (backward compat): start ALL ProcessingSteps for that order+phase that haven't started yet (batch start behavior, needed for Phase 3 VISTA-02)
- Return True if at least one step was started

**`complete_phase()` changes:**
- Accept optional `article_id` parameter
- If `article_id` provided: complete the specific ProcessingStep for that article+phase
- If `article_id` NOT provided: complete ALL ProcessingSteps for that order+phase (batch complete)
- After completing, check order completion: query ALL ProcessingSteps for ALL articles in this order. If every step has `timestamp_fine`, mark order as SPEDITO and create notification
- Use `flag_modified()` for any JSON mutations (existing pattern)

**`complete_phase_partial()` changes:**
- This method currently accepts `article_indices` (list of ints). Refactor to:
  - Accept `article_ids` (list of UUID strings) OR `article_indices` (list of ints, for backward compat)
  - If `article_ids` provided: complete ProcessingSteps for those specific articles
  - If `article_indices` provided: resolve indices to Article UUIDs by querying articles ordered by creation, then complete those
  - After completing, check per-article completion and order-level completion same as complete_phase

**`get_order_details()` changes:**
- Query Article records for the order (from articles table, not JSON)
- For each Article, query its ProcessingSteps (by article_id)
- Derive per-article status:
  - `completed_phases`: list of phase names where ProcessingStep has timestamp_fine
  - `remaining_phases`: phases in required_phases not yet completed
  - `next_phase`: first phase in required_phases order that isn't completed (None if all done)
  - `is_completed`: True if all required_phases are in completed_phases
- Build response maintaining the SAME shape as current API response for backward compatibility:
  - `articles` list with `idx`, `name`, `code`, `qty`, `required_phases`, `completed_phases`, `next_phase`
  - ADD new field `article_id` to each article in response (needed by Phase 2 and 3)
  - `processing_steps` list aggregated from all articles' steps (same shape as before)
- For orders with NO Article records (pre-v1.1 data): fall back to existing JSON-based logic

**`get_orders_by_phase()` changes:**
- Query Article records that have the specified phase in their `required_phases`
- For each matching article, check if its ProcessingStep for that phase is not yet completed
- Return orders that have at least one article awaiting that phase
- Optimization: Use a JOIN query instead of loading all orders (addresses known issue from STATE.md)

**`get_all_orders_dict()` changes:**
- Include article count and article-level completion summary in response
- Keep same response shape for backward compatibility

**`update_order_articles()` changes:**
- When articles are updated, sync the Article records in the articles table:
  - Remove Article records no longer in the list
  - Add new Article records
  - Update existing ones (match by code+name or by position)
  - Recreate ProcessingSteps for new articles
- Also update the JSON `articles` column for backward compat

IMPORTANT patterns to follow:
- Every method: `session = get_session()` + try/except/finally with `session.close()`
- `session.rollback()` on exception, `session.commit()` on success
- `flag_modified(obj, 'field')` for JSON column mutations
- Italian docstrings and comments
- Print-based logging for important operations: `print("[DB] ...")`
