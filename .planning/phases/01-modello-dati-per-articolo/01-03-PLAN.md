  <name>Task 1: Update API routes and wire migration into startup</name>
  <files>app/backend/app.py, app/backend/__init__.py</files>
  <action>
**app.py changes:**

1. Add import for migration: `from .migrate_articles import ensure_articles_table, migrate_existing_orders`

2. After `initialize_database()` call, add migration calls:
```python
# Migrazione v1.1: assicura tabella articles e migra dati esistenti
ensure_articles_table()
migrate_existing_orders()
```
This runs on every server start — both functions are idempotent (safe to re-run).

3. **`create_order` route** — Update to pass articles with default required_phases:
   - Before calling OrderManager.create_order, ensure each article in the articles list has `required_phases`
   - If an article dict doesn't have `required_phases`, add default: `['LASER', 'PIEGA', 'SALDATURA', 'PULIZIA', 'SPEDIZIONE']`
   - Response shape stays the same (201 with order_id, cliente, data_consegna, articles, total_quantity)
   - ADD to response: `article_records` list with `[{id, name, code, qty, required_phases}]` for each Article DB record — this gives the caller the UUIDs

4. **`get_order` route** — No changes needed (already calls `OrderManager.get_order_details` which was updated in Plan 02)

5. **`start_phase` route** — Update to accept optional `article_id` in request body:
   - Parse `article_id = data.get('article_id')` from request JSON
   - Pass to `OrderManager.start_phase(order_id, phase, operatore, article_id=article_id)`
   - If article_id not provided, existing batch behavior kicks in (backward compat)

6. **`complete_phase` route** — Update to accept optional `article_id`:
   - Parse `article_id = data.get('article_id')` from request JSON
   - Pass to `OrderManager.complete_phase(order_id, phase, note, article_id=article_id)`
   - Response includes updated order_details (same as before)

7. **`complete_phase_partial` route** — Update to accept `article_ids` in addition to `article_indices`:
   - Parse `article_ids = data.get('article_ids', [])` — list of UUID strings
   - If `article_ids` provided, pass those. Otherwise fall back to `article_indices` (backward compat)
   - Pass to `OrderManager.complete_phase_partial(order_id, phase, article_ids=article_ids, article_indices=article_indices, note=note)`

8. **`get_orders_by_phase` route** — Update response to include `article_id` in each article entry:
   - The updated `OrderManager.get_order_details` already includes `article_id` per article
   - Ensure the response passes it through

9. **Add new endpoint** `GET /api/orders/<order_id>/articles`:
   - Returns the Article records for an order: `[{id, name, code, qty, required_phases, completed_phases, next_phase, is_completed}]`
   - This endpoint is needed by Phase 2 (Assegnazione Fasi UI) and Phase 3 (Viste Reparto)
   - Calls `OrderManager.get_order_details(order_id)` and returns just the articles list

10. **Add new endpoint** `PUT /api/orders/<order_id>/articles/<article_id>/phases`:
    - Accepts `{"required_phases": ["LASER", "PIEGA"]}` to update an article's assigned phases
    - This is needed by Phase 2 (FASE-01, FASE-03) — the backend support must exist now
    - Calls a new method or updates the article's required_phases and recreates ProcessingSteps
    - Returns `{success: true, article_id, required_phases}`
    - Validation: only allow phase changes for articles whose ProcessingStep for that phase has NOT started (timestamp_inizio is null)

**__init__.py changes:**
- If `__init__.py` is empty or just has package marker, add exports:
```python
from .models import Article, Order, ProcessingStep, OrderFile, OrderNotification
from .database import OrderManager
```
This isn't strictly required but makes the package cleaner for future imports.

IMPORTANT: Keep ALL existing routes working with their current request/response shapes. New fields are ADDITIONS, not replacements. Any frontend page that currently works must continue to work unchanged.
