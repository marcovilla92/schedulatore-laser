**Part A: Backend API enrichment (app.py)**

Modify the `get_orders_by_phase(phase)` route (line ~344) to return ALL articles that have the given phase in their `required_phases` and have NOT yet completed it (instead of only articles where `next_phase == phase`).

For each article returned, include a `phase_status` field with one of three values:
- `"in_attesa"` — the ProcessingStep for this article+phase exists but `timestamp_inizio` is NULL
- `"in_lavorazione"` — the ProcessingStep has `timestamp_inizio` set but `timestamp_fine` is NULL
- `"completato"` — the ProcessingStep has `timestamp_fine` set

Implementation approach:
1. After calling `OrderManager.get_order_details(order.id)`, filter articles where `phase` is in `article['required_phases']` AND `phase` is NOT in `article['completed_phases']`
2. For each matching article, determine `phase_status` by checking the ProcessingStep state. Since `get_order_details` already returns `completed_phases` and `next_phase`, derive status:
   - If `phase` is in `completed_phases` → skip (already completed, don't include)
   - Else: query `ProcessingStep` where `article_id == article['article_id']` and `fase == phase` to check if `timestamp_inizio` is set:
     - `timestamp_inizio` is NULL → `"in_attesa"`
     - `timestamp_inizio` is set, `timestamp_fine` is NULL → `"in_lavorazione"`
3. Add `phase_status` and ensure `article_id` is included in each article dict in the response
4. Sort articles in the response: `in_lavorazione` first, then `in_attesa` (per user decision on ordering)
5. Sort orders by: `data_consegna` ascending (urgent first), then by status (orders with in_lavorazione articles before orders with only in_attesa)

The enriched response per order should look like:
```json
{
  "id": "uuid",
  "cliente": "...",
  "total_quantity": 100,
  "data_consegna": "2026-03-01T00:00:00",
  "articles_in_phase": [
    {
      "article_id": "uuid",
      "idx": 0,
      "name": "...",
      "code": "...",
      "qty": 10,
      "phase_status": "in_attesa"
    }
  ]
}
```

Note: rename `articles_next_phase` to `articles_in_phase` in the API response since we now return articles in all statuses for this phase (not just "next phase" articles). Keep `articles_next_phase` as an alias for backward compat if any other consumer depends on it (check if dashboard or other pages use it — they don't, only department views use this endpoint).

For the ProcessingStep query, import the ProcessingStep model at the top of the function and use a single batch query per order to avoid N+1:
```python
from .models import ProcessingStep
# Inside the route:
steps_for_order = session.query(ProcessingStep).filter(
    ProcessingStep.order_id == order.id,
    ProcessingStep.fase == phase
).all()
step_by_article = {s.article_id: s for s in steps_for_order}
```

But since we're in app.py (not database.py), we need a session. Use OrderManager's pattern — add a helper method or query inline. The simplest approach: extend the data already in `get_order_details()` response. Each article already has `completed_phases`. We just need to check if the step is started. Two options:
- Option A: Add `started_phases` to the article dict in `get_order_details()` (in database.py)
- Option B: Query ProcessingStep directly in the route (in app.py)

Use **Option A** — it's cleaner and reusable. In `database.py`, inside `get_order_details()`, for each article in the v1.1+ path, compute `started_phases` (phases where `timestamp_inizio` is set but `timestamp_fine` is NULL) from `art_steps`. Add it to the article dict:
```python
started = [s.fase for s in art_steps if s.timestamp_inizio and not s.timestamp_fine]
# Add to article_statuses dict:
"started_phases": started,
```

Then in `app.py` get_orders_by_phase route, derive `phase_status`:
```python
if phase in article['completed_phases']:
    phase_status = 'completato'  # should not happen since we filter these out
elif phase in article.get('started_phases', []):
    phase_status = 'in_lavorazione'
else:
    phase_status = 'in_attesa'
```

**Part B: Rewrite laser.html**

Rewrite the JavaScript section of laser.html to use the enriched API response. Keep all existing CSS styles, navbar, HTML structure, and modal structure. Only modify the `<script>` section and the modal buttons area.

Key changes to implement (honoring ALL locked decisions from CONTEXT.md):

1. **renderOrders function**: For each order, show articles grouped by status:
   - Each article row shows: name, code, quantity (pz), and a status indicator
   - Status indicators (per decision):
     - "In attesa": default text in `var(--text-secondary)` color
     - "In lavorazione": cyan accent color (`var(--accent-cyan)`) with pulsing dot animation
     - "Completato": green color (`var(--accent-green)`), reduced opacity (0.5)
   - Card does NOT appear if all articles for this phase are completed (filter in renderOrders)
   - Sort cards: orders with data_consegna ascending (urgent first), then orders with in_lavorazione articles before in_attesa-only orders

2. **"Avvia Tutti" button**: Replaces the old "Inizia" button.
   - On click, calls `POST /api/orders/{id}/phase/LASER/start` with `article_id` for EACH article in `in_attesa` status (sequentially with for...of await to avoid race conditions, per established pattern from Phase 2).
   - If all articles are already in_lavorazione, button is disabled.
   - No confirmation needed (per decision: "azione reversibile").
   - After completion, show toast "Fase LASER avviata per N articoli" and reload data.

3. **"Completa" button**: Opens modal (existing pattern).
   - Modal now shows articles with checkboxes, using `article_ids` (UUID) instead of `article_indices` (legacy int).
   - Each checkbox shows: article name, qty, and current status badge.
   - Articles already completed for this phase: checkbox checked + disabled + "Completato" badge.
   - "Seleziona Tutti" button in modal to check all non-completed checkboxes.
   - On submit, sends `POST /api/orders/{id}/phase/LASER/complete-partial` with `article_ids: [uuid1, uuid2, ...]` (NOT article_indices).
   - After completion, toast message + close modal + reload data.

4. **Add CSS** for the 3 article status states inside the existing `<style>` block:
   - `.article-status-attesa { color: var(--text-secondary); }`
   - `.article-status-lavorazione { color: var(--accent-cyan); }` with pulsing dot via `::before` pseudo-element
   - `.article-status-completato { color: var(--accent-green); opacity: 0.5; }`

5. **Use `articles_in_phase`** (new field name) instead of `articles_next_phase` in the JavaScript.

6. **Empty state**: Keep existing pattern — "Nessun Lavoro — Non ci sono articoli in attesa per questa fase" with check icon.

7. **Auto-refresh**: Keep existing 5-second interval.

8. **updateSummary**: Update to count from `articles_in_phase`, excluding `completato` articles from the "in attesa" count display.
